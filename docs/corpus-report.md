# 语料测试报告

对读取内核（`oco-docx`）做的第一次全面测试：用公开测试集检验健壮性、速度和读取结果的正确性，记录发现的问题、已修复的部分和剩余的差距。

由此得出的方向性结论在 [如何做得比现有方案更好](strategy.md)；Word 的具体行为规则在 [Word 实测行为](word-behaviour.md)。

## 结论摘要

- **健壮性**：4725 个文件，打开 4682 个（99.1%），无一崩溃。打不开的 43 个是加密文件、被错误命名的其他格式和故意损坏的测试文件。除一个使用默认密码的加密文件外，LibreOffice 能打开的 docx 我们都能打开。
- **速度**：全部文件单核 3.6 秒读完。同样的文件 python-docx 用 15.6 秒，mammoth.js 用 44.9 秒。
- **正确性**：正文段落的字符格式和段落格式，与 LibreOffice 的差异都在 0.3% 左右或更低（下划线除外，0.67%，原因见下）。差距集中在表格和列表，因为表格样式和编号还没有实现。
- **与 Word 一致性**：370 组 Word 另存对照中，一致的从 50% 提高到 83%。
- 测试过程中发现并修复了 18 类问题，新增 20 个回归测试。其中一处是内核按规范写、而 Word 实际行为相反的地方。

## 一、语料

用 `tools/corpus/fetch.sh` 从九个公开仓库拉取，共 4725 个文件、249 MB。语料不入库。

|---|---|---|

| docx4j | 1360 | 含 373 个 Word 365 另存的对照文件 |
| Open XML SDK | 503 | 微软官方 SDK 的测试文件，含 Office 模板 |
| Apache POI | 190 | 含模糊测试产生的损坏文件 |
| pandoc | 148 | |
| Apache Tika | 84 | |
| ONLYOFFICE 模板 | 50 | |
| python-docx | 46 | |
| mammoth.js | 17 | |

**语料的局限**，解读后面的数字时需要记住：

- 这些是测试文件，偏小（96% 小于 100 KB），偏重边界情况，不代表日常文档的分布。
- 75% 由 Word 保存，6% 由 LibreOffice 保存，其余未注明。
- 以中日韩文字为主的只有 33 个（0.7%）。

## 二、健壮性

| | 打开 | 比例 | 说明 |
|---|---|---|---|
| 本内核 | 4682 | 99.1% | 无崩溃；8 个带警告打开 |
| LibreOffice 24.2 | 4629 | 98.0% | 另有崩溃 11 次、超时 8 次（上限 45 秒） |
| mammoth.js 1.13 | 4614 | 97.7% | |
| python-docx 1.2 | 4332 | 91.7% | 打不开的文件中，110 个是模板或启用宏的文件类型，157 个找不到主文档关系（多为 ISO Strict 文档） |

我们打不开的 43 个文件：

| 数量 | 原因 | 是否应当支持 |
|---|---|---|
| 13 | OLE 容器：加密文档，或错误命名的旧版 .doc | 加密文档应当支持，尚未实现 |
| 4 | 实际是 OpenDocument（.odt） | 属于另一种格式，现在能明确识别并报告 |
| 19 | zip 结构或压缩数据损坏 | 模糊测试文件，拒绝是合理的 |
| 6 | 正文 XML 损坏 | 其中 2 个含 DTD，出于安全考虑一律拒绝 |
| 1 | 编码声明损坏 | |

与 LibreOffice 对照：它能打开而我们打不开的只有 6 个，即上面的 4 个 odt、1 个使用默认密码的加密文件和 1 个旧版 .doc。python-docx 和 mammoth.js 各有 2 个它们能打开而我们不能的文件，都是含 DTD 或数据损坏的测试文件。

测试中做的改进：样式、主题、设置这些部件损坏时，不再拒绝整个文档，而是用默认值打开并给出警告（8 个文件因此可读）。

## 三、速度和内存

| | 全部文件耗时 | 中位数 | 95 分位 | 最慢 |
|---|---|---|---|---|
| 本内核（原生，单核） | 3.6 秒 | 0.43 毫秒 | 1.6 毫秒 | 265 毫秒 |
| python-docx | 15.6 秒 | 1.7 毫秒 | 10.0 毫秒 | 286 毫秒 |
| mammoth.js | 44.9 秒 | 4.5 毫秒 | 25.6 毫秒 | 3238 毫秒 |
| LibreOffice（仅加载） | 297 秒 | 36 毫秒 | 145 毫秒 | 超时 |

各工具做的事不完全相同：我们读取全部内容并计算每段文字的最终格式；python-docx 读取并遍历段落；mammoth.js 提取纯文本；LibreOffice 做完整导入和排版。这张表说明的是量级，不是严格的同项比较。

最大的文档（正文 XML 12.6 MB，1.6 万个段落）：

| | 耗时 | 峰值内存 |
|---|---|---|
| 本内核（原生） | 约 250 毫秒 | 120 MB |
| 本内核（WASM，在 Node 中） | 约 600 毫秒 | 82 MB |
| python-docx | 832 毫秒 | 235 MB |

读取内核编译成 WASM 的体积是 300 KB，gzip 压缩后 144 KB（按体积优化编译）。

两个发现：

- 时间的 94% 花在解压和构建 XML 树上，计算样式继承只占 6%。
- 峰值内存约为 XML 大小的十倍。原因是先建完整的 XML 树再转换。改为流式解析可以大幅降低。

## 四、与 LibreOffice 的差分对比

用 `tools/corpus/lo_dump.py` 让 LibreOffice 导出它对每个文档的理解（每段文字的最终格式），再用 `tools/corpus/compare.py` 与我们的结果逐字符对比。LibreOffice 是另一套独立实现，两者一致的地方大概率是对的，不一致的地方值得查看。**它不是标准答案**，本次就发现了几处它与 Word 不同而我们与 Word 相同的地方。

两者都能打开的文档有 4623 个。

### 文字

| 指标 | 结果 |
|---|---|
| LibreOffice 的文字在我们的结果中出现的比例 | 99.7% |
| 文字完全相同的文档 | 3830 个（82.8%） |

我们多出的文字主要来自：LibreOffice 把浮动表格放在正文流之外；它重新计算域并显示"引用源未找到"，而我们显示文件里保存的结果。我们缺少的文字主要来自：嵌套超过 64 层的表格（一个压力测试文件嵌套了 5000 层）。另有约 40 个探测文档，我们按 Word 的方式读出了内容而 LibreOffice 读不出，也计入了"不相同"。

### 格式

在文字能对齐的段落上逐字符比较，表中是不一致的比例：

| 属性 | 正文 | 列表 | 表格内 |
|---|---|---|---|
| 粗体 | 0.05% | 0.01% | 1.35% |
| 斜体 | 0.00% | 0.00% | 0.02% |
| 字号 | 0.02% | 0.01% | 0.25% |
| 字体 | 0.07% | 0.01% | 0.08% |
| 下划线 | 0.67% | 0.12% | 0.02% |
| 删除线、大写、隐藏 | 均不超过 0.12% | | |
| 对齐 | 0.00% | 0.00% | 2.69% |
| 段前间距 | 0.31% | 3.96% | 1.22% |
| 段后间距 | 0.08% | 3.66% | 27.73% |
| 左缩进 | 0.01% | 2.89% | 0.17% |
| 首行缩进 | 0.00% | 8.44% | 0.23% |

解读：

- **正文段落**：样式继承的计算是可靠的。剩余的下划线差异来自目录：目录项带有超链接字符样式，LibreOffice 不显示它的下划线，我们按样式显示了。Word 在目录里同样不显示，这一条需要实现。
- **表格**：差异来自表格样式。表格样式可以规定单元格内段落的间距、对齐，以及首行加粗这类条件格式，目前完全没有实现。
- **列表**：差异来自编号定义里的缩进，目前没有实现。

## 五、与 Word 的对照

docx4j 的测试资源里有 370 组文件：一个手工构造的探测文档，和 Word 365 打开它之后另存的结果。Word 另存时只写规范的标记，所以另存结果记录了 Word 的理解。如果我们读探测文档的结果与读另存结果的一致，说明我们的理解与 Word 相同。检查脚本是 `tools/corpus/word_pairs.py`。

| | 一致 | 文字不同 | 格式不同 |
|---|---|---|---|
| 测试前 | 185（50%） | 166 | 18 |
| 修复后 | 306（83%） | 60 | 3 |

另有 1 组的探测文档含 DTD，被我们拒绝。剩余 64 组不一致的构成：

| 数量 | 原因 | 处理 |
|---|---|---|
| 28 | Word 另存时重新计算了域 | 不属于读取差异 |
| 13 | 未知元素的更细规则 | 仅见于探测文档，暂不处理 |
| 11 | 文档根部更极端的写法 | 同上 |
| 4 | zip 包内有重名条目 | 已解决：换成自己写的 zip 读取层后，这 4 份与 Word 一致，总数升到 311 |
| 3 | 换行符直接出现在正文里 | 待补 |
| 2 | Word 另存时丢掉了它实际画出的高亮 | 另存结果在这里不可靠 |
| 1 | 主题颜色 | 待实现 |
| 2 | 其他 | |

|---|---|---|---|

| 13 | 段落里直接出现的换行、制表符被忽略 | Word 对照 | |
| 14 | 自动段间距未读取 | LibreOffice 对比 | 正文段间距差异从 3% 降到 0.3% 左右 |

| 16 | 行距规则被单独继承 | docx4j 的记录 | 只写行距值时应回到"倍数" |
| 17 | 带小数的整数被四舍五入 | docx4j 的记录 | Word 直接截断 |

## 九、如何重现

```sh
tools/corpus/fetch.sh                                   # 拉取语料到 ./corpus
cargo build --release
target/release/oco corpus corpus                        # 健壮性、速度、未支持清单
python3 tools/corpus/survey.py corpus                   # 原始文件统计
python3 tools/corpus/word_pairs.py corpus               # 与 Word 另存结果对照
python3 tools/corpus/lo_dump.py --out corpus-lo corpus  # LibreOffice 参照，约 10 分钟
python3 tools/corpus/compare.py corpus-lo               # 差分对比
```

后三步需要 Python 3；`lo_dump.py` 另需 LibreOffice 及其 Python 绑定。语料来自各仓库当时的最新提交，`fetch.sh` 会把提交号记录在 `corpus/SOURCES.txt`，数字会随上游变化略有不同。
