# 路线图

## 目标

做一套完全自研的云端 Office 内核，能在浏览器和 App 内以 SDK 形式渲染并编辑文档，支持修订（跟踪更改）和内容增删。格式范围是 Word、Excel、PDF，之后是 PPT。

"自研"的边界：文档模型、排版引擎、编辑内核、格式读写由本项目自己实现；zip 解压、XML 解析、字形处理这类基础设施使用现成的库。

为什么这样做能超过现有方案，见 [如何做得比现有方案更好](strategy.md)。

## 已定的技术决定

| 决定 | 理由 |
|---|---|
| 内核用 Rust，编译成 WASM 和原生库 | 各端排版结果一致；大文档性能好；同一份内核可在服务端做转 PDF、出缩略图 |
| 以 Word 的实际行为为准，而不是规范的字面 | 两者有出入，使用者拿来对比的是 Word。见 [Word 实测行为](word-behaviour.md) |
| 还原度靠语料对比来衡量 | 每次改动是进步还是退步要有数字。见 [语料测试报告](corpus-report.md) |
| 依赖只用 MIT、Apache、BSD、Zlib 协议 | 避开 GPL 和 AGPL，保证代码可自由分发和商用 |
| 字体只用开源可商用字体，并做替换表 | 宋体、微软雅黑等字体不可随 SDK 分发 |
| 先做 Word（docx） | 文字排版引擎是 PPT 文本框、Excel 富文本、导出 PDF 的共同基础 |

### 字体替换

| 文档中的字体 | 替换为 | 协议 |
|---|---|---|
| 宋体、新宋体 | 思源宋体 | OFL |
| 黑体、微软雅黑、等线 | 思源黑体 | OFL |
| 楷体 | 霞鹜文楷 | OFL |
| 仿宋 | 待选型 | |
| Arial、Times New Roman、Courier New | Liberation Sans、Serif、Mono | OFL |
| Calibri、Cambria | Carlito、Caladea | OFL |

西文的几款替换字体与原字体字符宽度一致，换行位置基本不变。中文替换字体的行高和标点宽度与原字体有差异，影响程度要在原型 2 中实测。

## 原型阶段

用五个小原型回答最关键的问题，再决定正式架构。每个原型的代码都可能重写。

| # | 原型 | 要回答的问题 | 通过标准 | 状态 |
|---|---|---|---|---|
| 1 | 解析 | 文档模型有多复杂 | 对任意 docx 输出每段文字的最终格式 | 已完成，并经语料测试 |
| 2 | 排版 | 换行和分页能与 Word 对齐到什么程度 | 纯文字文档的换行位置和页数与 Word 一致 | 引擎已能排版正文；行高与 Word 实测一致；网格和标点规则尚未用 Word 验证 |
| 3 | 编辑 | 自绘界面上的输入体验是否可行 | 光标、选区、中文输入法可用，输入后局部重排 | 未开始 |
| 4 | 写回 | 能否做到无损保存 | 修改一段并带修订标记，Word 打开不报错，其余内容不变 | 未开始 |
| 5 | 嵌入 | 内核在各端的体积和性能 | 在浏览器和 iOS、Android 中运行，记录体积、启动时间、内存 | 有初步数据：读取内核的 WASM 为 300 KB |

### 原型 1 的结果

`oco-docx` 能读取 docx 并计算最终格式：

- 容器：通过部件关系定位主文档、样式、主题、设置；支持 Transitional 和 ISO Strict；单个部件有大小上限；可选部件损坏时带警告打开。
- 结构：段落、文字块、表格（含嵌套）、制表符、换行、符号字符，超链接和内容控件等包装元素，兼容性标记。
- 修订：插入、删除、移出、移入，带作者和时间。
- 格式继承：文档默认值、段落样式链、字符样式链、直接格式。
- 主题字体：按文档语言解析成具体字体名。
- 属性值按 Word 的读法解析，无效值的处理与 Word 一致。

语料测试的结论（详见 [报告](corpus-report.md)）：

- 4725 个公开测试文件，打开 99.1%，无崩溃，单核 3.6 秒读完。
- 正文段落的格式与 LibreOffice 的差异在 0.3% 左右或更低。
- 370 组 Word 另存对照，83% 一致。

得到的认识：

1. **格式不能直接读出来，必须算出来**，而且要按 Word 的算法算。规范没说清或说得不同的地方不少。
2. **差距集中在表格和列表**，原因是表格样式和编号定义还没有实现。
3. **公开语料里几乎没有中文文档**（0.7%），而中文文档依赖的文档网格、字符单位缩进在其他文档里很少见。
4. **内存是 XML 大小的十倍**，需要改为流式解析。

### 原型 2 的进展

`oco-layout` 把文档排成页面，`oco render` 输出每页一个自包含的 SVG。规则和依据见 [排版研究](layout.md)。

- 已覆盖：字体选择与替换、字号、粗斜体和各种字体效果、缩进（含字符单位）、对齐、行距、段间距、文档网格、制表位、多级编号（含中文数字格式和样式关联）、避头尾和行尾标点、分页和与下段同页。
- 行高、段间距合并、编号标签位置、上标尺寸这几项，用 Word 导出的 PDF 的实测值写成了测试。
- 自制了 10 份中文版式测试文档（公文、合同、规章、论文、报告等）。与 LibreOffice 对比，92.2% 的行断行位置相同。
- 对 4682 个公开文档全部完成排版，无崩溃。

- 建立了以 Word 为准的还原度度量：`tools/fidelity/score.py` 一条命令出记分表，基线按文档逐份记录，只许升不许降。对照 Word 365 导出的 128 份 PDF，87.7% 的行断行相同；只含正文、字体齐全的文档里，Word 记下的分页位置还原了 78%。方法和数字见 [还原度](fidelity.md)。

最重要的认识：**中文文档的行高取决于原字体的度量**。替换字体时必须保留原字体的度量，否则在文档网格下行距翻倍，这是基于 LibreOffice 的方案在中文文档上页数不对的根源。

## 下一步

1. **用 Word 验证中文排版规则**。在装有 Word 的 Windows 机器上运行 `tools\word\export.ps1`，把 `testdata/zh` 的 10 份文档导出为 PDF 并提交。之后记分表会多出逐行对照一栏，网格行高、标点挤压等目前靠推定实现的规则也可以量出来。这一步需要你或同事操作。
2. **收集真实的中文业务文档**。自制文档覆盖机制，不能代替真实文档。
3. **把记分表接入持续集成**。度量和基线已经就绪，目前靠提交前手工运行。
4. **继续原型 2**：表格的剩余部分（按内容定列宽、合并单元格、标题行重复、浮动表格；现在逐行对照 Word 丢失最多的一类）、图片、脚注。表格的网格列宽、单元格边距、行高和跨页拆行，以及页眉页脚和页码已经实现。
5. **补齐读取内核**，按影响排序：表格属性和表格样式、主题颜色、域。
6. **流式解析和自有 zip 读取层**。降低内存，去掉 WASM 下多余的依赖，并为按需加载做准备。
7. 根据原型 2 的结果确定正式的文档模型。原型 4 要求无损写回，因此模型需要保留不认识的内容，而不是像现在这样只做统计。

## 待定事项

- 字体度量替换的法律边界。
