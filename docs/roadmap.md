# 路线图

## 目标

做一套完全自研的云端 Office 内核，能在浏览器和 App 内以 SDK 形式渲染并编辑文档，支持修订（跟踪更改）和内容增删。格式范围是 Word、Excel、PDF，之后是 PPT。

**当前阶段的目标（已定）：先把预览做到极致。** 范围是三类文档：DOCX、DOC（Word 97 到 2003 的二进制格式）和 Markdown。编辑和修订、Excel、PDF 都排在这之后。

**三种格式，一个内核。** 不管文件是什么，都从同一种"文档形式"显示：一个 WordprocessingML 包，也就是 docx 文件本来的样子。DOC 和 Markdown 先转成这样一个包，之后的读取、排版、绘制与 docx 走完全相同的代码（入口在 `crates/oco-formats`）。这样做有三个好处：三种格式的版面同源，一处改进三处受益；转出来的包就是一个 Word 能打开的 .docx，转换本身是一项功能（`oco convert`）；同一个 .docx 可以交给 WPS 打开，Markdown 和 DOC 的显示效果因此也能逐行对照、可以度量。

"自研"的边界：文档模型、排版引擎、编辑内核、格式读写由本项目自己实现，zip 解压、XML 解析、字体文件解析这类基础设施也自己写。理由不只是"掌握在自己手里"：通用库的行为与 Word 不同的地方，换成自己的代码才改得了。第一个例子是 zip 包里的重名条目，通用库取后一个，Word 取目录里的前一个，换掉之后 4 份探针文档读得和 Word 一样了。命令行工具（开发用）输出 JSON 报告时仍用 serde，它不进入内核。

为什么这样做能超过现有方案，见 [如何做得比现有方案更好](strategy.md)。

## 已定的技术决定

| 决定 | 理由 |
|---|---|
| 内核用 Rust，编译成 WASM 和原生库 | 各端排版结果一致；大文档性能好；同一份内核可在服务端做转 PDF、出缩略图 |
| 以 Word 的实际行为为准，而不是规范的字面 | 两者有出入，使用者拿来对比的是 Word。见 [Word 实测行为](word-behaviour.md) |
| 还原度靠语料对比来衡量 | 每次改动是进步还是退步要有数字。见 [语料测试报告](corpus-report.md) |
| 内核不依赖第三方库 | 行为可以逐条对着 Word 校准；WASM 里没有多余的东西；不受别人的发布节奏和协议变化牵制 |
| 开发工具的依赖只用 MIT、Apache、BSD、Zlib 协议 | 避开 GPL 和 AGPL，保证代码可自由分发和商用 |
| 浏览器接口手写，不用绑定生成工具 | 模块不引入任何外部符号，任何能加载 WASM 的宿主（浏览器、App 里的网页视图、服务端）都能直接用 |
| 字体只用开源可商用字体，并做替换表 | 宋体、微软雅黑等字体不可随 SDK 分发 |
| 先做 Word（docx） | 文字排版引擎是 PPT 文本框、Excel 富文本、导出 PDF 的共同基础 |

### 字体替换

| 文档中的字体 | 替换为 | 协议 |
|---|---|---|
| 宋体、新宋体 | 思源宋体 | OFL |
| 黑体、微软雅黑、等线 | 思源黑体 | OFL |
| 楷体 | 霞鹜文楷 | OFL |
| 仿宋 | 待选型 | |
| Arial、Times New Roman、Courier New | Liberation Sans、Serif、Mono | OFL |

## 原型阶段

用五个小原型回答最关键的问题，再决定正式架构。每个原型的代码都可能重写。

| # | 原型 | 要回答的问题 | 通过标准 | 状态 |
|---|---|---|---|---|
| 1 | 解析 | 文档模型有多复杂 | 对任意 docx 输出每段文字的最终格式 | 已完成，并经语料测试 |
| 2 | 排版 | 换行和分页能与 Word 对齐到什么程度 | 纯文字文档的换行位置和页数与 Word 一致 | 引擎已能排版正文；行高与 Word 实测一致；网格和标点规则尚未用 Word 验证 |
| 3 | 编辑 | 自绘界面上的输入体验是否可行 | 光标、选区、中文输入法可用，输入后局部重排 | 未开始 |
| 4 | 写回 | 能否做到无损保存 | 修改一段并带修订标记，Word 打开不报错，其余内容不变 | 未开始 |
| 5 | 嵌入 | 内核在各端的体积和性能 | 在浏览器和 iOS、Android 中运行，记录体积、启动时间、内存 | 浏览器已通：完整内核 483 KB（gzip 后 212 KB），查看器在 Chromium 里实测可用，排出的页面与原生版逐字节相同。iOS、Android 未做 |

### 原型 1 的结果

`oco-docx` 能读取 docx 并计算最终格式：

- 容器：通过部件关系定位主文档、样式、主题、设置；支持 Transitional 和 ISO Strict；单个部件有大小上限；可选部件损坏时带警告打开。
- 结构：段落、文字块、表格（含嵌套）、制表符、换行、符号字符，超链接和内容控件等包装元素，兼容性标记。
- 修订：插入、删除、移出、移入，带作者和时间。
- 格式继承：文档默认值、段落样式链、字符样式链、直接格式。
- 主题字体：按文档语言解析成具体字体名。
- 属性值按 Word 的读法解析，无效值的处理与 Word 一致。

语料测试的结论（详见 [报告](corpus-report.md)）：

- 4725 个公开测试文件，打开 99.1%，无崩溃，单核 3.6 秒读完。
- 正文段落的格式与 LibreOffice 的差异在 0.3% 左右或更低。
- 370 组 Word 另存对照，83% 一致。

得到的认识：

1. **格式不能直接读出来，必须算出来**，而且要按 Word 的算法算。规范没说清或说得不同的地方不少。
2. **差距集中在表格和列表**，原因是表格样式和编号定义还没有实现。
3. **公开语料里几乎没有中文文档**（0.7%），而中文文档依赖的文档网格、字符单位缩进在其他文档里很少见。
4. **内存是 XML 大小的十倍**，需要改为流式解析。

### 原型 2 的进展

`oco-layout` 把文档排成页面，`oco render` 输出每页一个自包含的 SVG。规则和依据见 [排版研究](layout.md)。

- 已覆盖：字体选择与替换、字号、粗斜体和各种字体效果、缩进（含字符单位）、对齐、行距、段间距、文档网格、制表位、多级编号（含中文数字格式和样式关联）、避头尾和行尾标点、分页和与下段同页。
- 行高、段间距合并、编号标签位置、上标尺寸这几项，用 Word 导出的 PDF 的实测值写成了测试。
- 自制了 11 份中文版式测试文档（公文、合同、规章、论文、报告、带页眉页脚的手册等）。与 LibreOffice 对比，92.2% 的行断行位置相同。
- 对 4682 个公开文档全部完成排版，无崩溃。

- 建立了以 Word 为准的还原度度量：`tools/fidelity/score.py` 一条命令出记分表，基线按文档逐份记录，只许升不许降。对照 Word 365 导出的 128 份 PDF，94.1% 的行断行相同，83.5% 的行位置在 0.5 磅以内；只含正文、字体齐全的文档里，Word 记下的分页位置还原了 80%。方法和数字见 [还原度](fidelity.md)。

最重要的认识：**中文文档的行高取决于原字体的度量**。替换字体时必须保留原字体的度量，否则在文档网格下行距翻倍，这是基于 LibreOffice 的方案在中文文档上页数不对的根源。

## 下一步

1. **继续原型 2**：分栏、VML 写的老式图片和文本框。图片（行内和浮动）、文本框、表格、页眉页脚和页码、脚注和尾注已经实现；图片还缺两侧同时排字和 EMF、WMF 的绘制，表格还缺浮动表格和条件格式。段落和单元格的边框、底纹已实现。
2. **查看器**：字体解析、排版、查找和页面绘制已放到后台线程；支持全文查找、高亮、跳页、文字选择和复制，缩放时保持阅读位置。下一步按文档用到的字体按需加载（现在按固定顺序分批加载完整字体集，约 170 MB），并继续验证真实大文档。
3. **中文规则的参照**：以 WPS 导出的 PDF 为参照继续校准（已定：不等 Word 的中文导出）。有 Word 的机器时，`tools\word\export.ps1` 仍可随时把 `testdata/zh` 导出来补上。
4. **收集真实的中文业务文档**。自制文档覆盖机制，不能代替真实文档。
5. **补齐读取内核**，按影响排序：表格样式的条件格式、形状的主题色和渐变、更多域。文字、下划线、段落与表格边框和底纹的主题色已实现；页眉页脚已支持分节页数和显式页码格式。
6. **流式解析和按需加载**。zip 读取层已经是自己的，可以在它上面做范围请求：先取目录，再取正文，图片用到时才取。
7. **编辑和写回**（原型 3、4）。文档模型要先改成保留不认识的内容，而不是像现在这样只做统计；zip 写出目前只有不压缩的一种，写回前要补上压缩。
8. **把记分表接入持续集成**。度量和基线已经就绪，目前靠提交前手工运行。

## 待定事项

- 项目的开源协议。
- 仿宋的替换字体（目前用思源宋体代替，字形不像）。
- 中文语料的来源和存放方式（真实文档涉及隐私和体积，不宜入库）。
- 字体度量替换的法律边界。
